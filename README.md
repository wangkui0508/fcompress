# 32×32 FP16 分列 8bit 量化：Apple Silicon / NEON 实现

把 32×32 的 FP16 矩阵按**列**压成 `uint8`，每列附带 `min` 和 `step` 两个 FP16，
反量化为 `v = min + step * x`。

```
原始   : 32*32*2B            = 2048 B
压缩后 : 1024 B(q) + 64 B(min) + 64 B(step) = 1152 B   →  1.778x
```

> 压缩比与矩阵规模无关：每 32 个值固定 32B 载荷 + 4B 开销，**开销占 12.5%**。
> 这个格式的天花板就是 1.78x。

---

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| 用 `fdiv` 算 `1/step`，能换成取倒数提速吗？ | **不能。除法在这台机器上完全不是瓶颈**，换 `vrecpe` 反而慢 1% |
| 那真正的瓶颈在哪？ | **量化的运算域**。把量化从 f32 搬到 f16 域，编码快 **1.9x** |
| 代价？ | `q` 最多差 1 个 LSB，实测重建 SNR 最差掉 **≤ 0.75 dB**（数据相关），`step` 与参考**逐位相同** |
| 有什么坑？ | f16 存 `step` 有精度悬崖；f16 取倒数会溢出；**f16 域的 `v-min` 也会溢出**（后两者已加守卫回退） |

本机（Apple M5 / clang 21 / `-O3 -mcpu=apple-m1`）实测，L2 常驻
（多次运行有 ±3% 波动，下面取代表值）：

```
compress  :  ~59 ns/块    (f16 量化快路径)
             ~111 ns/块   (f32 量化高精度路径)
decompress:  ~27 ns/块
```

---

## 1. 三个决定性的设计选择

### (1) 不转置 —— `q` 保持行主序，而不是按列连续

"每列压成 uint8"很容易让人第一反应是先把 32×32 转置，让一列变成连续 32 个元素。
**不要这么做。** 转置一次在入口，反量化写回时还要再转一次，两头都白付代价。

改成：

| 数组 | 布局 | 说明 |
|---|---|---|
| `q` | `q[r*32 + c]`，行主序 | 和输入同构，写回时无需重排 |
| `min[32]` / `step[32]` | 按列 | 连续 8 个列共 16B，刚好一条 `vld1q_f16` |

于是：

- **压缩时**每行 32 个 f16 = 4 条 `float16x8_t`，一趟扫描用 4 组向量累加器
  同时维护 32 列的 min/max —— 不需要转置，不需要水平规约。
- **解压时** `min[c..c+7]` / `step[c..c+7]` 就是连续 8 个 f16，直接向量加载广播，
  没有 gather、没有 shuffle。

**全流程零转置、零 lane 重排。**

### (2) min/max 规约留在 f16 域

`vminq_f16` / `vmaxq_f16` 对 f16 是**精确**的（min/max 不产生舍入）。
只有当 `mn16`/`mx16` 进入 `step` 计算时才转 f32。

### (3) 两条路径共用同一套 min/step，只在量化域上分叉

```c
void fc_compress_neon(...)      // 默认：f16 域量化 + 溢出守卫（快 1.9x）
void fc_compress_neon_hp(...)   // 高精度：f32 域量化，与标量参考逐位一致
```

`step` / `min` 由**同一段代码**产生（都是 `vdivq_f32` + 窄化到 f16），所以两条路径
落盘的数据只在 `q` 上有 ±1 的差别，`step` 逐位相同。

## 2. 指令级配方

### 共享：两趟扫描

```
Pass 1 — 求 32 列 min/max（31 行 × 4 组）
    mn[g] = vminq_f16(mn[g], v)     // f16 域, 精确
    mx[g] = vmaxq_f16(mx[g], v)

中间 — 每 8 列一组
    step16 = vcvt_f16_f32(vdivq_f32(vsubq_f32(mx, mn), 255.0f))
    vst1q_f16(out->min  + g*8, min16)    // min 是 f16 原值, 精确
    vst1q_f16(out->step + g*8, step16)
```

### 快路径量化：每 8 元素 6 条指令

```
    e      = vrecpeq_f16(step16)                    // FRECPE.8H
    e      = vmulq_f16(vrecpsq_f16(step16, e), e)   // 1 次 Newton -> ~2^-11
    inv16  = vbslq_f16(vceqq_f16(step16, 0), 0, e)  // 常量列保护
```

```
    v = vld1q_f16(row)              // 8 个 f16
    t = vmulq_f16(vsubq_f16(v, mn), inv16)   // FSUB.8H + FMUL.8H  <- 8 元素一条!
    u = vcvtnq_u16_f16(t)           // FCVTNU.8H: f16->u16, 就近偶数 + 饱和
    vst1_u8(dst, vqmovn_u16(u))     // 夹到 [0,255]
```

关键在于 **f16 域一条指令处理 8 个元素，而且 ARM 有 f16→u16 的饱和转换指令**
（`FCVTNU.8H`）。负数被饱和到 0，`vqmovn_u16` 再夹到 255，**不需要任何显式 clamp**。

### 高精度路径量化：每 8 元素 ~13 条指令

```
    vl = vcvt_f32_f16(vget_low_f16(v))      // f16x8 -> f32x4 ×2
    t  = vmulq_f32(vsubq_f32(vl, mnl), invl)
    u  = vcvtnq_u32_f32(t)                  // FCVTNU.4S
    n16 = vcombine_u16(vqmovn_u32(u_lo), vqmovn_u32(u_hi))
    vst1_u8(dst, vqmovn_u16(n16))
```

> ARMv8 的 ISA 有 `FCVTZU.4S, Vn.4H`，但 **ACLE 没有暴露 f16→u32 的 intrinsic**
> （`vcvtq_u32_f16` 不存在）。**f16→u16 有**（`vcvtnq_u16_f16` 等 5 种舍入模式全在），
> 这正是快路径能成立的前提。

### 解压：每 8 个输出 5 条指令

```
    x16 = vmovl_u8(vld1_u8(qrow))       // u8 -> u16
    xf  = vcvtq_f16_u16(x16)            // -> f16, 精确
    y   = vfmaq_f16(mn, xf, st)         // min + q*step, 单次舍入
    vst1q_f16(orow, y)
```

`min`/`step` 的 8 条向量 load 会被编译器提出行循环，内层只剩
`ld1 / ushll / ucvtf / fmla / st1`，行与行完全独立。

## 3. 为什么不用取倒数换掉 fdiv？（做了完整对照实验）

直觉上"除法比乘法贵"，应该把 `1/step` 换成 `vrecpeq_f32` + Newton 迭代。
**实测不成立。** 9 个变体的完整对照（`make variants` 可复现）：

| 变体 | `range/255` | `1/step` | 量化域 | 耗时 | vs 基线 |
|---|---|---|---|---|---|
| A | `vdiv` | `vdiv` | f32 | 111.2 ns | — |
| B | `vmul(1/255)` | `vdiv` | f32 | 111.1 ns | −0.2% |
| C | `vmul(1/255)` | `vrecpe`+1×Newton | f32 | 112.0 ns | +0.7% |
| D | `vmul(1/255)` | `vrecpe`+2×Newton | f32 | 113.2 ns | +1.7% |
| E | `vmul(1/255)` | `frecpe`+1×Newton | **f16** | **57.4 ns** | **−48%** |
| E0 | `vmul(1/255)` | `frecpe`（无 Newton） | **f16** | 56.0 ns | −50% |
| ET | `vmul(1/255)` | `frecpe`+1×Newton | **f16**/截断 | 57.5 ns | −48% |
| **FAST** | `vdiv` | `frecpe`+1×Newton | **f16** | **58.5 ns** | **−47%** |
| **HP** | `vdiv` | `vdiv` | f32 | 111.4 ns | 基线 |

**A/B/C/D 全在 111~113 ns，差 1.7% 以内。** 8 条 `VDIV.4S` 相互独立，
延迟被后面 pass 2 的计算完全掩盖了 —— 除法在这个 kernel 里是**免费**的。
把除法换成 `VRECPE/VRECPS`（Apple 上吞吐受限）反而净亏。

**真正的杠杆是量化域**：E 系列把 pass 2 从 13 条指令压到 6 条，直接砍掉一半时间。

### 但快路径有三个必须处理的坑

**坑 1：截断 vs 就近舍入（ET vs E）。**

| | pat0 SNR |
|---|---|
| E（`vcvtnq_u16_f16`，就近偶数） | 54.57 dB |
| ET（`vcvtq_u16_f16`，截断） | **49.03 dB** |

截断引入 −0.5 LSB 的系统性偏置，**直接掉 5.75 dB**。必须用 `vcvtnq_u16_f16`。

**坑 2：f16 倒数溢出（E0 是精度不够，E 是溢出）。**

`step` 小的时候 `1/step` 会超出 f16 上限 65504：

- `step < 1/65504 = 1.527e-5`（等价 `range < 3.9e-3`）时 `inv16 = +inf`，
  整列直接烂掉 —— **不是精度下降，是完全错误**。
- 实测 pat6（`range = 5e-4`）：SNR 从 51.53 dB 崩到 **0.32 dB**，`max|Δq| = 255`。

Fast 路径用两道守卫解决：

```c
/* 守卫 1: 把 step==0 换成 65504 后取全部 32 列的最小值 */
acc = vminq_f16(acc, vbslq_f16(vceqq_f16(step16[g], 0), 65504, step16[g]));

/* 守卫 2: 取全部 32 列 f16 域跨度 mx-mn 的最大值 */
rng = vmaxq_f16(rng, vsubq_f16(mx[g], mn[g]));

if ((float)vminvq_f16(acc) < 2.0e-5f || (float)vmaxvq_f16(rng) > 65504.0f) {
    /* 回退 f32 量化 */
}
```

- 阈值取 `2e-5`（inv ≤ 50000，留 24% 余量对抗 `FRECPE` 的估计误差）。
  实测 `FRECPE.8H` 原始估计的最大相对误差是 **0.27%**（限"真值倒数能装进 f16"的范围内），
  而且这段范围内它从不返回 `inf`，所以 24% 余量是安全的。
- **`step == 0` 的常量列不触发回退**（两条路径都正确），否则常量列会让整个块白白变慢。
- 两道守卫合计成本在噪声内（58.2 vs 60.0 ns/block，多次运行取最小）。

无 Newton 的 E0 更快（56.0 ns）但 SNR 掉 1.9~2.3 dB（`FRECPE` 只有 ~8 bit），
**一次 Newton 迭代必须保留**。

**坑 3：f16 域 `v-min` 溢出（最隐蔽的一个，实测 `max|Δq|` 可达 127）。**

量化在 f16 域做 `v - min`。`min` 和 `v` 本身都是 f16，但**差值不保证还是 f16**：
当某列跨度 `mx - min > 65504`（f16 最大有限值）时，`v - min` 溢出成 `+inf`，
`inf * inv` 仍是 `inf`，`FCVTNU` 把它饱和到 65535、`vqmovn` 夹到 255 —— 该列顶部
整段被压成 255，而参考实现给出的是正常的 128~255。实测：

| min | max | range | fast `max\|Δq\|` | fast SNR | 参考 SNR |
|---|---|---|---|---|---|
| −32752 | 32752 | 65504（边界） | 0 | 48.8 dB | 48.8 dB |
| −30000 | 40000 | 70000 | 8 | 34.4 dB | 48.8 dB |
| −60000 | 60000 | 120000 | **115** | **4.3 dB** | 48.5 dB |
| −65504 | 65504 | 131008（f16 全域） | **127** | −inf | — |

守卫 2 直接测 f16 域的 `mx - min` 是否溢出，**不去测 f32 的 `range > 65504`**：
`range` 落在 (65504, 65520) 时 f16 差值仍然有限，只损失不到 1 个 LSB，不必回退。

> 这个坑在归一化到 O(1) 的数据上永远碰不到，只在"不做归一化、且列内同时有大正数和
> 大负数"时暴露。修复前的测试数据全是 `base + range*u`（`base` 最大 1000、`range`
> 最大 1500），没有任何一列跨越正负大数量级，所以该 bug 在原始测试里是隐形的。
> 现在 `test_fcompress.c` 的 pattern 6/7/8 专门覆盖这一档（在旧代码上会红：
> `max|Δq| = 1 / 113 / 127`）。

**两道守卫都是块级的**：32 列里只要有 1 列命中，整块都走慢路径。实测单列
`range = 3.1e-3` 就能让整块从 58 ns 变 115 ns（**1.97x**）。真实数据里的"近似常量列"
（偏置、padding、全零通道）很常见，所以编码耗时有双峰，调用方需要知道这一点。
想消掉它就得把回退细化到 8 列一组（或按列），目前没做。

## 4. 唯一的实质风险：FP16 存 `step` 的精度悬崖

`step = range/255` 比 `range` 本身小约 8 个二进制位，所以 **range 偏小时 step 会掉进
f16 次正规区**（`|x| < 2^-14 ≈ 6.1e-5`），有效位数骤降到 1~2 位。两条路径**同样受影响**。

实测（`./test_fcompress` 第 2b 节）：

```
   列   range(f32)     step=range/255   f16(step)       相对误差   f16 状态
    0   4.721e-04    1.851e-06    1.848e-06   1.89e-03   次正规! 精度骤降
   12   4.663e-04    1.829e-06    1.848e-06   1.04e-02   次正规! 精度骤降
   24   4.778e-04    1.874e-06    1.848e-06   1.38e-02   次正规! 精度骤降
    4   4.722e+02    1.852e+00    1.852e+00   1.32e-04   正常
  -> 次正规/零 step 列数: 6/32,  最大相对误差 1.38e-02
```

**1.38% 的 step 相对误差 = 3.5 个量化台阶**，这些列的等效 SNR 从 ~48dB 掉到 ~35dB。

判定阈值：

- `range < 255 * 2^-14 ≈ 1.56e-2` 时 step 进入次正规区，精度开始明显退化。
- 更狠的是**吸收效应**：若 `min` 很大（如 1000，f16 ulp = 0.5）而 range 很小，
  `min + step*x` 在 f16 里直接塌缩成 `min`，整列信息全丢。
  需要 `range ≳ 256 * ulp(min)` 才有意义。

**这不是 NEON 的问题，是"用 2 字节 FP16 存 step"这个格式的固有上限。** 处理办法：

1. **最佳**：压缩前把每列归一化到 O(1)（range ≥ 0.1 量级），格式完全够用。
2. 把 step 的编码换成"尾数 + 隐含的 2 的幂"，或干脆扩成 f32（压缩比降到 1.71x）。
3. 至少在压缩端断言，把次正规 step 的列上报出来，别静默降质。

## 5. 正确性验证

`./test_fcompress` 全部通过：

| 检查 | 结果 |
|---|---|
| 高精度路径 `q`/`min`/`step` vs 标量参考（9 种模式，含常量列与满量程/超量程列） | **bit-exact** |
| 反量化 vs double 精度参考（单次舍入，等价 FMA 语义） | **0 ULP**；230 万块随机对拍同样 **0 ULP** |
| 快路径 `step` vs 参考 | **逐位相同**（230 万块、20.5 亿 lane 零例外） |
| 快路径 `q` vs 参考（9 种模式 × 1024） | `Σ\|Δq\| = 153`，`max\|Δq\| = 1` |
| 快路径 `q` vs 参考（200 万块随机，限 `mx-min ≤ 65504`） | `max\|Δq\| = 1`（≈4.7% 的 lane 差 1 个 LSB） |
| 列跨度 > 65504（pat7/8，`range` 最大 131008） | 守卫回退，`max\|Δq\| = 0`；修复前为 8 / 113 / 127（见坑 3） |
| 快路径 ΔSNR | 内置 9 种模式最差 **−0.34 dB**；200 万块随机对拍实测最差 **−0.75 dB** |
| 每列 `min` 精确复现 & 端点偏差 | 精确 / ≤ 0.119 × step（上界 0.5） |
| 小 range 块（pat5, `range=5e-4`） | 自动回退，输出与参考**逐位相同** |
| 重建 SNR（range 混合数量级） | 54.6 ~ 64.6 dB |

> 标量参考刻意复刻 f32 路径的运算顺序，所以能要求 bit-exact 而不是"差不多"。

**未覆盖 / 前置条件**：NaN / ±Inf 输入。NEON 的 `FMIN/FMAX` 会把 NaN 当缺失值跳过，
标量版在首元素为 NaN 时会污染整列，两者行为不一致 —— 这个前置条件现在直接写在
`fcompress.h` 的 API 注释里，请在入口断言输入有限。

另外注意 **字节流可复现性**：快路径内部用了实现定义的 `FRECPE.8H`，
`q` 不保证跨芯片世代/工具链一致；需要确定性字节流（落盘、校验、上游比对）时
用 `fc_compress_neon_hp`，它是 f32 域计算、与标量参考逐位一致。

## 6. 文件与用法

| 文件 | 内容 |
|---|---|
| `fcompress.h` | API 与布局约定（`fc_block`，16B 对齐） |
| `fcompress_neon.c` | NEON 编解码主体（快路径 + 高精度路径） |
| `fcompress_ref.c` | 标量参考实现（对拍用） |
| `test_fcompress.c` | 正确性 + 精度诊断 + 性能 |
| `bench_variants.c` | 9 变体对照实验（回答"能不能不用 fdiv"） |
| `Makefile` | 构建与探针 |

```bash
make check-arch        # 确认 __ARM_FEATURE_FP16_VECTOR_ARITHMETIC
make asm               # 看实际生成的 NEON 指令直方图
make && ./test_fcompress 8192
make variants          # 复现第 3 节的对照实验
```

编译要求：`-mcpu=apple-m1` 及以上（或 `-march=armv8.6-a+fp16`）。
M1 及之后所有 Apple Silicon 都带 FP16 向量算术，不需要 f32 模拟。
